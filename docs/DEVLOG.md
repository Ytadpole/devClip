## 怎么读这份文件

条目**按 `git log --reverse` 的顺序**排列，也就是时间顺序。校验：

```bash
grep -oE '^## [0-9a-f]{7}' docs/DEVLOG.md | awk '{print $2}' > /tmp/dl.txt
git log --format='%h' --reverse > /tmp/gl.txt
diff /tmp/dl.txt /tmp/gl.txt
```

**本文件原本是 gitignore 的本地笔记**，`2c02b75` 起纳入版本库。
所以那之前的条目是**事后补录**的：那些 commit 推送时并没有带上对应
记录，是本文件入库时一次补上的。内容本身当时就写在本地笔记里，
只是补录时点晚于 commit —— 读的时候不必当成「当时就记下了」。

最后一条没有条目：条目无法包含自己这个尚未产生的 hash。所以校验脚本
的预期结果是**只差最后一行**。

## fbc207c · 2026-09-27 · fix: 选中态色条错位并溢出到下一行

压到下一行，肉眼很明显；之前行高是 `auto` 时它按比例摊在行尾。

改成 `left-[-2px] top-0`。绝对定位色条时这两点都要显式写。

**动作查找之外还要查「适不适用」。** 原来只按 action id 找动作，
不确认它对这条记录的 `content_type` 适用。UI 只会给出适用的动作，
所以这条防线平时不触发；它是给「invoke 传了别的类型的动作」兜底的 ——
否则一句普通文本会被当 JSON 解析，报一个跟用户操作对不上的错。

判断走 `ContentType: FromStr`（数据库里存的是字符串）。这条路径

## 61ff541 · 2026-09-30 · fix: 剪贴板去重改成只比内容，敏感项不再被顺延到永不过期

真机验收时看到库里同一段文本 `copy_count` 到了 11。根因是去重做成了
「内容相同**且**在 800ms 窗口内」，而轮询一圈实际要 1 秒以上 ——
`read_text()` 与入库都有开销，窗口比真实周期窄，于是每轮都判成新内容。

**窗口式去重在这里根本不成立。** 任何「比时间」的判据都要赌轮询周期
比窗口短，而这个周期不是常数：机器慢一点、数据库锁等久一点就失效。
只比内容没有这个依赖 —— 剪贴板没换过东西就是没有新的复制事件。

**真正严重的后果是敏感项永远不过期。** 每次重复入库都会顺延
`expires_at`，密钥在剪贴板里躺得越久、TTL 越往后推，「60 秒后自动
消失」这条验收在真机上根本不成立。单元测试全绿也没抓到：测试拿
`POLL` 的名义值构造观察时刻，而真机上的实际周期比它大。

代价：「隔很久又复制了同一段、且中间没复制过别的」区分不出来，
`copy_count` 少加一次 —— 那条记录本来就在历史里。中间复制过别的
再复制回来（a → b → a）照常算两次。

顺带清掉两个 clippy 警告（CI 带 `-D warnings`，本地却一直当噪音）：
`emit_monitor_unavailable` 只有 Linux 路径调用，跟着同一个 cfg 走；
