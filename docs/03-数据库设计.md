# 03 · 数据库设计

## 核心表

第一版只要**一张业务表 + 一张 FTS5 虚表**。不要一开始就搞十几张表。

```sql
-- 迁移版本管理（SQLite 内置，不建表）
PRAGMA user_version = 1;

PRAGMA journal_mode = WAL;      -- 读写并发，历史写入与前端查询不互相阻塞
PRAGMA busy_timeout = 5000;     -- 写锁冲突时等待而非直接报错
PRAGMA foreign_keys = ON;

CREATE TABLE clipboard_item (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    content        TEXT,
    content_hash   TEXT    NOT NULL UNIQUE,   -- blake3(content)，去重依据
    content_type   TEXT    NOT NULL,          -- text/json/jwt/sql/url/uuid/base64/ip/exception/commit/markdown/code/image
    preview        TEXT,                      -- 列表显示用，截断到 ~200 字符
    image_path     TEXT,                      -- 图片走文件系统，不进 BLOB
    byte_size      INTEGER NOT NULL DEFAULT 0,
    copy_count     INTEGER NOT NULL DEFAULT 1, -- 重复复制累加，不新增行
    source_app     TEXT,                      -- macOS/Windows 可取前台应用名
    created_at     INTEGER NOT NULL,          -- 首次进入历史的时间
    last_copied_at INTEGER NOT NULL,          -- 最近一次复制的时间（排序用这个）
    favorite       INTEGER NOT NULL DEFAULT 0,
    sensitive      INTEGER NOT NULL DEFAULT 0, -- 疑似密钥/token，见下方"敏感信息"
    expires_at     INTEGER                     -- 到期自动清除（秒级时间戳）
);

CREATE INDEX idx_item_recent   ON clipboard_item(last_copied_at DESC);
CREATE INDEX idx_item_favorite ON clipboard_item(favorite, last_copied_at DESC);
CREATE INDEX idx_item_type     ON clipboard_item(content_type, last_copied_at DESC);
CREATE INDEX idx_item_expiry   ON clipboard_item(expires_at) WHERE expires_at IS NOT NULL;
```

## 全文搜索（FTS5 + trigram）

**用 `trigram` 分词器，不要用 `porter` 或默认的 `unicode61`。**

原因：搜代码需要的是**子串匹配**。

| 搜索词 | `unicode61` | `trigram` |
|---|---|---|
| `ser` | ✗ 匹配不到 `select` | ✓ 命中 |
| `use` | ✗ 匹配不到 `user` | ✓ 命中 |
| `redis` | ✓ | ✓ |
| `sk_live_` | ✗（下划线被切断） | ✓ |

`unicode61` 把 `sk_live_abc123` 切成 `sk` `live` `abc123`，搜 `live_abc` 完全匹配不上。这对剪贴板这种"随手搜中间一段"的场景是致命的。

```sql
CREATE VIRTUAL TABLE item_fts USING fts5(
    content,
    content = 'clipboard_item',     -- 外部内容表：只索引 content 列，省空间
    content_rowid = 'id',
    tokenize = 'trigram'
);

-- 用触发器保持同步
CREATE TRIGGER clipboard_item_ai AFTER INSERT ON clipboard_item BEGIN
    INSERT INTO item_fts(rowid, content) VALUES (new.id, new.content);
END;

CREATE TRIGGER clipboard_item_ad AFTER DELETE ON clipboard_item BEGIN
    INSERT INTO item_fts(item_fts, rowid, content) VALUES ('delete', old.id, old.content);
END;

CREATE TRIGGER clipboard_item_au AFTER UPDATE ON clipboard_item BEGIN
    INSERT INTO item_fts(item_fts, rowid, content) VALUES ('delete', old.id, old.content);
    INSERT INTO item_fts(rowid, content) VALUES (new.id, new.content);
END;
```

查询（关联回主表取其他字段）：

```sql
SELECT c.* FROM clipboard_item c
JOIN item_fts f ON f.rowid = c.id
WHERE item_fts MATCH ?
  AND c.favorite = 0
ORDER BY c.last_copied_at DESC
LIMIT 50;
```

**trigram 的两个注意点：**

1. 需要 SQLite ≥ 3.34（trigram 分词器是 3.34 引入的）。`rusqlite` 的 `bundled` feature 自带足够新的 SQLite，OK。
2. 查询串要做转义。trigram 模式下 `MATCH` 的查询语法有自己的引号规则，用户输入的 `"`、`*`、`-` 等字符需要处理。经验做法：**对关键词做 `replace` 转义后整体加双引号**，当作短语匹配。

## 去重策略

剪贴板管理器的历史如果不做去重，重复按 `⌘C` 就能刷出几百条重复项。

规则：

```
收到内容 → 计算 blake3 hash
  ├─ 已存在（hash 命中）
  │    ├─ copy_count += 1
  │    ├─ last_copied_at = now
  │    └─ 仍按原 content_type 存储（用户可能复制了一段新 JSON，内容变了 hash 就不同，不存在这个问题）
  └─ 不存在
       └─ INSERT 新行
```

配合两条过滤：

- 与**当前剪贴板内容**完全一致 → 直接丢弃
- 与**DevClip 自己刚写入的内容**一致 → 丢弃（回环保护，见 [02 架构设计](02-架构设计.md) 事件流第 ③ 步）

## 图片存储

**不要把图片存成 BLOB。** 原因：会让 FTS 虚表的 rowid 对齐、主表查询和 vacuum 全都变慢，收益为零。

```
$APPDATA/devclip/images/
├── 2026-09-26/
│   ├── a1b2c3d4.png          原始图（按 hash 命名天然去重）
│   └── a1b2c3d4_thumb.png    缩略图，列表用
```

主表只存 `image_path` 和 `byte_size`。大小上限建议 **10 MB**，超限则只存缩略图并在 UI 提示"图片过大，仅保存预览"。

### macOS 的 text / image 双 flavor

从浏览器或 IDE 复制一段文字时，NSPasteboard 里**同时**有纯文本和多种富文本 flavor。处理规则：

```
① 有纯文本 flavor → 只存文本
② 无文本、只有图片 → 存图片
③ 两者都有 → 存文本，图片忽略
   （避免一行 SQL 被存成图片，这会直接毁掉搜索体验）
```

## 敏感信息

开发者天天复制 API Key、token、`.env` 内容、SSH 私钥。这是剪贴板管理器被用户抵制的**头号原因**，所以从第一版就要处理。

自动标记为 `sensitive = 1` 的规则：

| 特征 | 示例 | 实现 |
|---|---|---|
| AWS Access Key | `AKIA` + 16 位 | ✅ |
| 私钥块 | `-----BEGIN … PRIVATE KEY-----` | ✅ |
| GitHub PAT | `ghp_` / `gho_` / `ghu_` / `ghs_` / `ghr_` + 36 位 | ✅ |
| Stripe | `sk_live_`（`test` 是公开的，不算） | ✅ |
| Slack | `xoxb-` + 15 位 | ✅ |
| 云厂商密钥 | `pk_live_*`、`xoxa-` / `xoxp-` / `xoxr-` / `xoxs-` | ✗ |
| JWT | `eyJ...` 三段 base64url | ✗ |
| 显式赋值 | `(password\|passwd\|secret\|token\|api_key)\s*[:=]\s*\S+` | ✗ |

**实际只做前五条，宁可漏报也不误报。** 把一段普通 SQL 判成密钥，
用户会立刻把这个功能关掉，那漏报就变成了真问题。后三条没做是有理由的，
不是漏了：JWT 本身就是一种内容类型，标成敏感反而没法搜；显式赋值会命中
`token = null` 这类占位符与文档片段；剩下的云厂商前缀格式不够固定，
凑不齐「不会误报」这条标准。

命中的是不是真 token，要看**前后是不是边界** —— 少这个判断，
`mask_live_xxx`、`mask_live` 都会被当成真密钥，而 `?key=sk_live_xxx`
这种嵌在 URL 里的仍要命中。所以判定是「长度固定 + 前后不挨着字母数字
或下划线」，不是简单的 `contains`。

命中后：

- UI 上打锁形图标，默认**不参与**普通搜索结果（需要主动展开"含敏感信息"分组）
- `expires_at` 默认设为 `now + 60s`，后台定时任务到期自动删除并清空剪贴板
- 用户可关闭该行为（设置项 `sensitive.auto_expire`）

## 后续版本的表（现在不要建）

```
tags            标签：#docker #java #redis（P1）
item_tag        多对多关联（P1）
```
