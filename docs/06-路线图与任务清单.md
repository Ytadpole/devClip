### 阶段 1 偏离清单

实现与原清单不一致的地方，记下来免得后面当成 bug 查：

- **收藏键从 `Space` 改成 `⌘D`。** 搜索框常驻焦点，`Space` 必须留给打字。
  `↑↓` / `Home` / `End` 以及 cmdk 自带的 `⌃J⌃N` / `⌃K⌃P` 也一并接管了，原因见下。
- **键盘导航从 cmdk 手里拿走了。** cmdk 靠在 DOM 里查
  `[cmdk-item][aria-selected="true"]` 定位当前项，`↑↓` 也在已渲染的项之间跳。
  列表虚拟化之后它只看得到窗口内的项，两处都会算错，`Enter` 甚至会静默失效。
  现在 ↑↓ 由 `Palette` 接管，cmdk 只留 `Input` / `Empty` / `Item` 的 aria 与点击。
  **要守住一条：selected 那一项必须始终留在 DOM 里**
  （`VirtualList` 用 pin 区间 + 滚动 effect 兜底）。
- **行高是跨文件常量。** `VirtualList.ROW_H` 与 `ItemRow` 的 `h-[62px]` 必须一起改，
  改一处就会滚动错位。
- **mock 补了 120 条批量数据。** 28 条手写数据在 420px 视口里只占 7 行，
  触发不了窗口滚动，虚拟化有没有生效根本看不出来。

### 阶段 3 实现笔记

`cargo test` 67 条、`cargo clippy` 0 警告、`cargo fmt` 已规范。

**踩到的三个真 bug（都是测试逼出来的，不是我看出来的）：**

- **base64url 字母表写成标准 base64。** 用了 `+` `/`，而 base64url 是 `-` `_`。
  JWT 签名里的 `_` 因此被拒，`jwt_valid` 一直红。`jwt_minimal` 造的样本
  不含 `-_`，所以它一直绿 —— 测试数据的运气好掩盖了实现错误。
  已补 `jwt_with_url_safe_chars`，改回错字符集时它会红。
- **DDL 规则用 `contains` 吞散文。** 为了让 `CREATE TABLE t (id INT)` 单条即命中
  而放宽，结果 `we will create table later` 也被判成 SQL。已改成必须匹配行首，
  并补 `sql_ddl_word_in_prose_not_sql` 锁住。
- **异常裸类名被「必须含 `.`」挡掉。** `RuntimeError: msg` 没有包名。
  现在规则是「有包名限定 **或** 冒号后带 message」，反例是
  `there was an Exception yesterday`。

**两处规则是刻意偏离 docs/04 的原始描述**（原描述在实测中不成立）：

- **围栏代码块单独即判 markdown**，不要求凑满 2 类。代码块和 code 的区别
  就在这对 ```，要求第二类会把它判成 code。
- **DDL 单关键字即判 SQL**，`SELECT` 之类仍需 2 个。`CREATE TABLE users (...)`
  全文只有一个 SQL 关键字。

**「6379」被判成 json 是正确行为**，裸数字是合法 JSON。精度测试里原本
把它期望为 text，是标注写错了，已改。这条是 JSON 规则优先级的必然结果。

### 阶段 4 实现笔记

**`models.rs` 没有单独建文件。** `ClipboardItem` 和它的 serde 落在
`repo.rs` 顶部 —— 只有一个结构体时单独开文件只是形式。

**trigram 搜不到两字词，这条比清单里写的更严重。** trigram 按 3 字符
切分，「中文」「用户」「会议」这类两字词一律命中 0 条，中文里却满地都是。
现在 `>=3` 字符走 FTS5，`<3` 回退 `LIKE`（并给 `LIKE` 补 `%` `_` 转义，
不转的话搜「50%」会匹配全表）。

性能实测见 DEVLOG 的 `114469d`：全量 13.11ms，子串 3–4ms，最慢的
两字中文 `LIKE` 2.94ms，都在 50ms 线内。

> **Rust 学习价值：** 错误处理（`anyhow` / `thiserror`）、`Connection` 的生命周期、与 C FFI 交互。

### 阶段 5 实现笔记

清单里有三处与实现不符，不是 bug，是当初没想到的地方：

- **没有 `ClipboardMonitor` trait，是 `spawn_watcher` 按 `cfg` 分派。**
  两个平台各一套循环，抽象不出共同的东西；强行套 trait 只会得到一堆
  永远返回默认值的样板方法。平台差异大到需要各自的回环处理时，
  trait 就成了负担。
- **剪贴板读写用 `arboard` 而不是自己写 `NSPasteboard`。** 跨平台、
  无 unsafe。macOS 上**读**剪贴板不需要任何授权（TCC 只拦辅助功能与
  Apple Events），所以前端权限表也不用加东西。
- **`paste.rs` 走 `osascript` 而不是 `CGEvent`。** CGEvent 在没有辅助功能
  授权时是**静默丢弃**的，用户只看到光标闪一下，没有任何提示。
  osascript 会以 `-1719` 明确退出，能翻译成「去 系统设置 → 隐私与
  安全性 → 辅助功能 勾选 DevClip」。代价是可能卡在 TCC 弹窗上，
  所以外面包了 3 秒硬超时 + kill，否则每次粘贴失败都留一个僵尸进程。

还有一处踩坑值得单记：**读前台应用不能用 osascript。**
`tell application "System Events"` 会触发 TCC「自动化」弹窗，弹窗不出现时
osascript 一直等，而调用方当时**持着数据库锁** —— 整个应用假死。
换成 `NSWorkspace` 的进程内调用，微秒级返回。

回环保护是 `SelfWrite` + `Seen` 两个结构：前者挡自己写进去的粘贴被
重新捕获，后者做去抖。见 DEVLOG 的 `ea56af7` —— 去抖窗口必须**每次
观察都推进**，否则按住 Ctrl+C 十秒会把 `copy_count` 刷到 11。

> **Rust 学习价值：** `async`/`await`、`tokio`、系统 API FFI、线程模型。难度陡增，但前面三阶段已经把语法基础打完了。

### 阶段 6 实现笔记

**`json.sort_keys` 删掉了，因为它是个空操作。** `serde_json::Map`
默认是 `BTreeMap`，不显式开 `preserve_order` 就天然按字母序输出。
查过依赖树确认没人开这个 feature，所以 `美化` 的结果已经排序了 ——
再挂一个同名动作，用户会以为「不点就没排」。详见 [04](04-内容识别与工具箱.md)。

**结果写进剪贴板，命令只返回摘要。** 格式化后的 JSON 几 KB，
状态栏一行、2.6 秒自动消失，塞不下也不该塞。写之前必须在
`SelfWrite` 记一笔，否则监听线程会把结果当成用户复制的内容再存一条。

**「+ 粘贴」没做，是产品决策不是实现难度。** 自动粘贴要抢焦点、
把调色板收起来 —— 而用户可能正想在结果出来之后留在调色板里继续操作。
现在拿 ⌘V 手动粘。要改的话得先想清楚这条。

**加 `hint` 字段（悬停可见）主要是为了 JWT。** payload 是 base64
编码、任何人可读，签名只保证「没被改过」—— 用户点之前就该知道。
这句话只能由后端给，因为它跟着实现走。

**`text` / `code` 也挂了 base64 编码动作**，代价是选中任何一句话
都会出现工具条。对开发者工具可以接受，换来的是「把一段命令编成
base64」这个常见需求不用换类型。

**mock 与 Rust 的动作列表必须逐条对齐。** 以前两边各写各的，
e2e 跑的是一套假列表，而真应用里点「Sort Keys」得到「没有这个动作」。
现在 e2e 有 4 条用例守着这件事。

### 阶段 6 没做的

- **`ip` / `exception` / `markdown` 没有动作。** `ip` 的进制转换与
  `exception` 的堆栈提取都简单，但都是低频需求，先不做
- **`Open in Browser` 没做。** 它需要 `AppHandle`，进不了纯函数注册表
- **编辑原条目（docs/04 通用操作里的 Edit）没做。** 要一个内置编辑器

### 阶段 7 实现笔记

**敏感规则只做明确无疑的。** 私钥块、AKIA+16、ghp_+36、`sk_live_`、
`xoxb-` 五条。宁可漏报也不误报 —— 把一段普通 SQL 判成密钥，用户会
立刻关掉这个功能。扫描点在 `capture()` 之前，两个平台的监听路径共用。

**敏感内容入库而不是跳过（推翻了早期的「不入库」）。** 不入库的版本
用户毫无感知 —— 复制了密钥，打开调色板什么都没有，只会以为 DevClip
坏了；而且密钥本来就已经明文躺在系统剪贴板里，历史里多存 60 秒
（有界）与「永久躺在剪贴板」相比不是新增的风险面。按 docs/03 的设计：
入库打标 → UI 打锁、默认搜不到（`includeSensitive` 分组）→ 60 秒后
后台任务删除并清空剪贴板；`sensitiveAutoExpire` 设置可关。

**保留期那条 prune SQL 显式排除 `expires_at IS NOT NULL` 的行**，否则敏感项
会被保留期清理提前删掉，等于绕过「到期才删」的设计。收藏项同理排除。
最大条数那条不排除 —— 它只会让敏感项更早消失，不是安全问题，但意味着
一批密钥能把正常历史挤出上限。

**验收是在真机上做的，并且抓到了一个单元测试抓不到的 bug。** 复制
`sk_live_…` 后查库：`sensitive=1`、`expires_at` 约等于 60 秒后、到期
行被删、剪贴板被清空。但第一次跑就看到同一段文本 `copy_count` 到了 11 ——
去重原本是「内容相同且在 800ms 窗口内」，而轮询一圈实际要 1 秒以上，
窗口比真实周期窄，每轮都被判成新内容，`expires_at` 因此被不断顺延，
敏感项等于永不过期。改成只比内容后重测：TTL 线性递减、`copy_count`
保持 1、60 秒后准点消失（见 61ff541）。UI 打锁与默认搜不到由 e2e 守
（mock 后端），SQL 默认排除由 `repo` 的单测守。

`retention = 0` 表示「立即过期」，会把非收藏的全删掉 —— 这条语义要记住。

### 亮色主题的实现约定

**`theme` 这一项早就躺在契约里了，只是没人消费。** Rust 侧一直在存
（`settings.rs` 的 `theme` 字段、`clamp_settings` 放行
`dark|light|system`），`SettingsPanel` 里还留着一句「UI 还没有亮色主题
可切，放一个不生效的开关是骗人 —— 不放」。这次的活儿全在前端。

**唯一开关点是 `<html>` 上的 `data-theme`，`src/lib/theme.ts` 只做
「设置里的取值 → 这个属性」，颜色一个字都不管。** 顺带解决了一个
隐患：如果直接让 `prefers-color-scheme` 驱动样式，用户在设置里选了
深色、系统是亮色时就有了两套来源，谁赢取决于 CSS 加载顺序。现在
「跟随系统」也走同一条路，由 `resolve()` 现算。

**配色分两套写法，这是有意的取舍：**

- 中性色（底、描边、文字、悬停层）走 `@theme` 变量，默认值就是深色，
  亮色在 `html[data-theme="light"]` 里整组覆盖。一处改，全局跟着变
- 强调色（13 种内容类型 + 状态色）用元素上的 `light:` 变体。
  放进变量的话是 13 × 2 = 26 个变量，而这张表本来就得在每个类型旁边
  同时写清深浅两色（`TYPE_META`），留在原地更好读

**亮色不是把深色反过来。** 两处刻意不同：画布用 `#fafafa` 不用纯白
（调色板是常驻窗口，长时间盯着白底刺眼），描边用发蓝的黑而不是把
深色的 alpha 搬过来（白底上的发丝线要更深才看得见）。`home/index.html`
的亮色早就这么定过，两边照着同一套值走。

**主题不经过设置页的草稿，点一下就落盘。** 数值字段是「打一半不该被
当成值」，主题没有中间态；跟着「保存设置」走的话，用户看见颜色变了
却以为没存下来。`loadTheme` 在 `init()` 里调，不等用户打开设置页。

**e2e 的状态栏钩子从配色类换成了 `[data-status]`。** 状态色跟着主题
走，浅色下 `text-emerald-400` 白底读不出来 —— 按类名找的话，改一次
配色就得改一次测试。`data-status` 顺带给出了 ok / warn / err。主题
测试则去读 `body` 的实际底色：只断言 `data-theme` 属性的话，少写一条
CSS 规则测试照样绿。

**托盘在 Linux 上是可用性前提，不是装饰。** X11 剪贴板内容存在持有者
进程里，进程一退就没了，所以必须常驻，而「怎么常驻」只能靠托盘 ——
没有它用户唯一能做的就是杀进程，那恰好是最容易丢数据的操作。
Tauri 2 把托盘内建成 `tauri::tray` 了，不需要 `tauri-plugin-tray`
（那个 crate 在索引里已经不存在）。

### 阶段 8 实现笔记

文件叫 `clipboard/linux.rs` 而不是清单里的 `x11.rs` —— 它不是「X11 的
剪贴板」，是「Linux 的剪贴板」，里面 Wayland 检测也在这。

**X11 走 Selection 机制：没有计数器可轮询**，只有一个 CLIPBOARD
selection 和它的持有者窗口。两个直接后果：只能靠持有者变化判断有没有
新内容；**持有者进程一死内容就没了** —— 所以不只是「读」，还必须**接管**，
自己变成持有者并一直应答别人的请求。

**四条不看文档猜不到的事实**（先用 `examples/x11probe.rs` 探出来的）：

- **CLIPBOARD 不是 X 预定义的原子**（`PRIMARY=1`、`SECONDARY=2` 才是），
  必须 `InternAtom` 按名问。本机值 438。写 `AtomEnum::CLIPBOARD` 编译不过
- arboard 的 `write()` 是**先接管再等**，不是反过来
- `set().wait()` 在内容被覆盖时**自己返回**，「我们不再是持有者」是
  **可精确通知**的（`JoinHandle::is_finished`），不用去猜自己的窗口 ID
- arboard 有**进程级全局单例**，同进程内所有 `Clipboard::new()` 共享
  同一个 X11 窗口

最后一条让最初的验收脚本只拿到 3/5：源程序和监听器在同一进程里，写入的
owner 窗口号前后相同，轮询根本看不见变化。**验收必须用独立进程模拟
「用户在别的程序里复制」**（`examples/linux_live.rs`），否则测的是一个
不存在的场景。

**监听用「owner 变化 + 每 2 秒兜底读」混合。** 纯 owner 轮询会漏掉两种
都很常见的情况：编辑器原地改内容再复制（owner 不变），以及系统已装了
别的剪贴板管理器时代替所有应用持有（owner 恒定）。

**`frontmost_app` 返回 X11 窗口 ID 而不是窗口标题。** 标题会变、可能重复，
更要命的是调色板抢到焦点时记下的就是「DevClip」。用 `_NET_ACTIVE_WINDOW`
客户端消息精确激活（带 `data[0]=2` 的源码指示，不带它不少 WM 会直接忽略）。
同时要排除自己作为 `source_app`，否则每条历史都写着「DevClip」。

**两处诚实记录，别当成「已验证」：**

- 「DevClip 退出后剪贴板内容仍在」**不是**接管生效的证据。查了发现是
  arboard 析构时把数据交给了**系统自带的剪贴板管理器**（Cinnamon 有）。
  换到没装剪贴板管理器的机器上不会这样。已验证的只是「源程序退出后内容
  仍在」，那才是接管的功劳
- 全局快捷键在这个环境里**无法自动验证** —— X 会话没有活动窗口
  （`xdotool getactivewindow` 返回空），合成按键无处可发。托盘图标
  创建无报错，但点不开验证

真机验收 5/5 捕获，密钥被拦下，检测延迟约 0.5s。

## 技术债与风险台账

| 项 | 级别 | 说明 | 缓解 |
|---|---|---|---|
| Wayland 无监听 API | 高 | 影响 Linux 新用户 | 明确降级 + 引导 X11 会话 |
| macOS 辅助功能授权 | 高 | 影响核心体验 | P0 就做降级路径 + 权限引导 |

| macOS 分发需公证 | 中 | 别人装不上 | 早期只自用 + GitHub Release 手动 |
| 团队只有一个人 | 高 | 范围容易膨胀 | 严守"阶段 5 之前不做 P1/P2" |
