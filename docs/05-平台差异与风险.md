# 05 · 平台差异与风险

DevClip 依赖的三类系统能力，在三个平台上的实现难度差异极大。**这是本项目最主要的技术风险，必须在设计阶段就明确。**

## 能力矩阵

| 能力 | macOS | Windows | Linux |
|---|---|---|---|
| **监听剪贴板变化** | NSPasteboard `changeCount` 轮询，~500ms | `GetClipboardSequenceNumber` 轮询，~500ms（放弃 `WM_CLIPBOARDUPDATE` 的理由见 docs/06 阶段 9 笔记） | X11 `CLIPBOARD_SELECTION` owner 事件 / **Wayland 无标准 API** |
| **写剪贴板** | `NSPasteboard` | `OpenClipboard` + `SetClipboardData` | X11 需抢占 ownership（进程退出即丢失） |
| **模拟粘贴** | `CGEvent` + `Cmd+V`，**需辅助功能授权** | `SendInput` + `SetForegroundWindow` | XTEST（`libxtst`） |
| **全局快捷键** | Carbon / `RegisterEventHotKey` | `RegisterHotKey` | X11 grab（**但 Super 键被 WM 占用**） |
| **获取前台 App** | `NSWorkspace.frontmostApplication` | `GetForegroundWindow` + `GetWindowThreadProcessId` | X11 `_NET_ACTIVE_WINDOW` |
| **焦点抢占** | `NSApp.activate(ignoringOtherApps:)` | `SetForegroundWindow`（受前台锁定限制） | `XSetInputFocus` |

---

## 风险 1：Linux 剪贴板监听（影响 V0.2）

### X11 —— 可行

X11 剪贴板是 **Selection 机制**：任何程序成为 `CLIPBOARD` selection 的 owner，selection 内容变化时 owner 会收到 `SelectionRequest`。标准做法是当 owner（clipboard manager 本身持有数据），配合 `XFixesSelectSelectionInput` 监听 `CLIPBOARD_SELECTION` 属性变化。

已有成熟 crate 可参考：`clipboard-master`（X11）、`wl-clipboard-rs`（Wayland）。

**好消息：Linux Mint 22 默认是 Xorg + Cinnamon，`DISPLAY` 环境正常，V0.2 直接走 X11 即可。**

### Wayland —— 没有标准 API

Wayland 刻意不暴露剪贴板读取权限。当前唯一的途径是非标准协议 `zwlr_data_control_manager_v1`（wlroots 生态）：

| 合成器 | 支持情况 |
|---|---|
| Sway / Hyprland / niri / river（wlroots 系） | ✓ |
| GNOME / Mutter | ✗ 明确不支持 |
| KDE Plasma | 部分版本 / 实验性 |
| Cinnamon + Muffin（Wayland） | 不确定，需实测 |

所以：

> **在 Wayland 会话下，本项目应当降级为"只读不监听"**，并在 UI 上明确提示"当前 Wayland 会话不支持自动监听，请使用 X11 会话"。

**降级方案（在 X11 会话登录时选）：** Linux Mint 的登录界面（SDDM/GDM）右上角齿轮 → 选择 **"Cinnamon on Xorg"**。

设计上必须把平台差异收敛到 `ClipboardMonitor` trait 里，见 [02 架构设计](02-架构设计.md)。**不要把 X11 逻辑焊死在业务代码里**，否则以后接 Wayland 要重写。

## 风险 2：模拟粘贴需要授权（影响全部平台）

粘贴是"**这个产品最重要的体验**"，但它恰恰是最容易失败的一环。

| 平台 | 机制 | 失败表现 |
|---|---|---|
| macOS | `CGEventPost` 发 ⌘V | **无辅助功能权限时静默失败**，用户只看到光标闪了一下 |
| Windows | `SendInput` | 前台窗口被抢走时，粘贴到错误窗口 |
| Linux | XTEST | 少数 WM 下失焦行为不同 |

### 必须在 P0 就实现的降级路径

```
尝试模拟粘贴
  ├─ 成功 → 结束
  └─ 失败/无权限
       └─ 只写入剪贴板
            └─ UI 提示："已复制到剪贴板，请按 ⌘V 手动粘贴"
               并在托盘菜单里给出"授予辅助功能权限"的入口
```

**不能让功能直接死掉。** 一个"能粘贴但偶尔要手动按一下"的版本，远好过一个"粘贴按钮点不动"的版本。

macOS 上还要在首次启动时主动检测权限状态（`AXIsProcessTrusted`），没权限就引导用户到"系统设置 → 隐私与安全性 → 辅助功能"。

## 风险 3：默认快捷键冲突

**`⌘⇧V` 是个坏默认值。**

- **macOS**：`⌘⇧V` 是 "Paste and Match Style"，Chrome / Slack / VSCode / JetBrains 都在用。全局注册会**直接抢掉这些应用的快捷键**，用户会认为 DevClip 是恶意软件。
- **Linux**：`Cmd` 映射为 Super 键，被窗口管理器占用，抓不到。

### 建议

| 平台 | 默认值 | 备选 |
|---|---|---|
| macOS | `⌥⌘V`（Option+Cmd+V） | `⌥⌘C` / `⌃⌘V` |
| Windows | `Win+Shift+V` | `Alt+V` / `Win+Alt+V` |
| Linux | `Alt+Shift+V` | `Ctrl+Shift+Space` |

### 必做

- 快捷键**持久化**，改过就记住
- 首次启动引导用户确认（不要用默认组合直接注册）
- 注册失败（被占用）要 `reject` 到前端，UI 明确提示"该快捷键已被其他程序占用"，并引导重设

## 风险 4：X11 剪贴板在进程退出后丢失

X11 的剪贴板是"借用"机制：只有当 owner 进程存活时数据才存在。所以：

- X11 环境下，**DevClip 必须常驻托盘**，不能复制完就退
- 这反过来验证了托盘图标是必需组件，不只是 nice-to-have
- macOS / Windows 无此问题（系统自己保存剪贴板历史）

## 风险 5：图片与文本双 flavor

从浏览器 / IDE 复制时，剪贴板里同时存在纯文本和富文本多种 flavor。若处理不当，一行 SQL 会被存成图片，直接毁掉搜索体验。

**规则：有纯文本就只存文本。** 详见 [03 数据库设计](03-数据库设计.md#图片存储)。

## 各平台发布注意事项

| 平台 | 阻塞项 |
|---|---|
| macOS | 分发需 Apple 开发者账号做 **公证(notarization)**，否则别人装不上。免费账号的 App ID 也可公证，但需在 CI 里存 `APPLE_ID` / `APPLE_PASSWORD` / `APPLE_TEAM_ID` |
| Windows | SmartScreen 误报，需要代码签名证书才能避免（无证书时用户需手动"更多信息 → 仍要运行"） |
| Linux | AppImage / deb 都可直接分发，无阻塞项。建议同时提供 AppImage |

## CI 注意事项

GitHub Actions 矩阵构建：

```yaml
strategy:
  matrix:
    include:
      - os: macos-latest     # aarch64 + x86_64
      - os: ubuntu-22.04     # WebKitGTK 依赖在此版本上最稳
      - os: windows-latest
```

用 `tauri-apps/tauri-action` 自动构建并上传到 GitHub Releases。Linux runner 上**不要用 ubuntu-24.04**（webkit2gtk 版本行为有变动，容易构建失败）。
